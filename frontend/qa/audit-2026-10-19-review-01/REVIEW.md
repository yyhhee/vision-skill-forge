# 当前前端体验与功能审核

日期：2026-10-19。对象：独立前端 `http://127.0.0.1:6174/`。

本轮只审核，没有修改应用代码、接入后端、重启原服务或提交 GitHub。用户当前编辑页只读观察；修改、应用和模拟运行均在隔离演示工作区执行。

## 总体结论

现有“场景画面 + 规则画布 + 右侧编辑器”的方向合理，值得保留。作为一个可操作的区域告警前端原型，主要流程已能走通；作为面向普通用户的通用视觉技能编辑器，还没有达到要求。

最重要的问题不是重新设计视觉风格，而是三处一致性：描述与规则、条件内部关联字段、所选版本与实际打开的运行任务。建议先修复这三项，再建设 12 完整保存与加载，以免归档一份含义不清的配置。

“尚未接入真实模型、LLM、视频与后端”是本阶段约定边界，不作为意外故障；模拟结果不能用来证明真实检测效果或运行正确性。

## 一、按用户操作顺序审核

### 1. 场景标注：基本合理，窄窗口操作需优化

大视口下，画面和资源列表的对应关系较清楚，适合保留。用户当前实际窗口约为 806 × 956 CSS 像素，出现页面、画面面板与资源区域的多层滚动，切换画面和规则的成本明显增加。

建议：窄窗口切换为“画面 / 规则 / 资源”清晰分区；侧栏可收起；保留当前技能名；尽量让同一操作区域只有一个主滚动容器。不必推翻已确认的大屏视觉。

### 2. 联动工作台与技能描述：有高优先级一致性问题

画布中目标、分支、组合与输出的表达方向正确。大屏比中小视口完整；1280 × 720 时右侧分支及下方输出需要额外移动或滚动才能看全。

本轮修改“一句话描述”为“区域1有穿蓝色上衣的人，且区域2至少4人时告警”，保存后标题更新，规则仍是红色上衣、灰色裤子、人数 ≥ 2。编辑框没有明确提示“仅修改说明，不重新编排”。应用也未要求解决该差异。

建议将两个动作分开：

- **修改说明**：明确不改变规则。
- **按新描述重新编排**：展示建议差异后确认；在尚未接入 LLM 时明确不可用，不假装已重新生成。

规则摘要应由实际配置生成，不能把可自由编辑的描述当作当前运行规则的证明。

![步骤2：描述已经变蓝色及4人，画布仍是红色及2人](/C:/Users/83915/Vision%20Skill%20Forge%20Frontend/qa/audit-2026-10-19-review-01/08-description-rule-drift.jpg)

### 3. 条件编辑：有保护机制，但关联字段缺少核对

优点：A/B 证据、组合方式、参数均可查看和修改；离开未保存表单时，有保存 / 放弃 / 继续编辑的保护。

复现：将红色条件的判断部位从上半区域改成下半区域，A 改为下半区域红色占比，B 仍是 `person wearing a red top`，名称仍是“红色上衣”，没有待核对提醒。

这不是简单地把所有字段强制联动：用户可能有意独立配置 A 和 B。通用处理应区分“系统生成”和“用户自定义”：生成值可随来源变更同步；自定义值保留，但来源变化时标为待核对，展示具体差异后由用户确认。该约束适用于任意目标、属性、部位与关系，不限穿戴。

### 4. 时间约束：对象指向更清楚，重复入口应合并

完整时间编辑器能显示作用于条件还是分支，以及关联区域等信息，方向正确。但分支编辑器同时提供简化时间配置，完整时间编辑器又有更多模式，同一时间要求出现两个编辑入口，容易产生“这是两次计时还是同一项设置”的疑问。

建议：分支卡只显示当前时间摘要与“编辑时间要求”，实际字段统一放到完整编辑器。按所选模式显示必要字段；条件时间和分支时间必须分别显示作用对象，不暗中叠加或覆盖。

![步骤4：完整时间要求编辑器](/C:/Users/83915/Vision%20Skill%20Forge%20Frontend/qa/audit-2026-10-19-review-01/desktop-editors/06/implementation.png)

### 5. 分支逻辑与编排组：组编辑已有基础，通用条件树不完整

编排组已有顺序、嵌套成员、调整顺序与时间间隔等可操作表单，适合继续迭代。

但分支编辑目前主要是平铺的 AND / OR 和已有条件；尚未形成清晰的新增条件 C/D、新增分支、NOT、分支内嵌套括号组的完整编辑链路。编排组可以嵌套，不等于分支内已经具备通用递归条件树。

建议保留现有可视化表达，在节点旁提供“添加条件 / 添加子组 / 排除 NOT”，并提供取消组合、移入与移出。条件类型应来自能力注册信息和输入输出兼容性约束，不按安全帽、服装等例子逐个增加专用页面。先补齐一个统一入口，不增加多套高级逻辑编辑器。

### 6. 业务输出、校验与应用：受控选择合理，缺少具体变更审阅

来源与结果类型已经是受控选择，错误面板可以定位问题，优于要求用户填写技术 ID。应保留这一方向。

问题是“应用全部草稿修改”的确认仍较笼统，用户难以确认本次到底会应用哪些条件、标注、时间、编排、输出和运行参数。

建议提供统一的“查看未应用修改”，按页面分组展示旧值 → 新值、关联影响和待核对项，并在确认处明确“将生成 R4，既有 R3 运行不改变”。没有变化时不要制造新版本。

### 7. 进入运行与版本选择：有高优先级版本歧义

“测试运行”先打开运行快照，用户还需选择“打开运行设置”，再开始模拟验证。建议主动作改为“运行验证”，直接进入设置并显示版本；“查看运行版本”作为次级动作。

更重要的复现：应用到 R4 后，设置页显示“使用已应用 R4”。已有未结束的 R3 任务时，点击“开始模拟验证”却打开旧 R3 任务。界面会提示“已打开尚未结束的模拟任务；请继续或取消”，但没有先提示 R3/R4 冲突并让用户选择。

建议明确提供“继续 R3 旧任务 / 停止旧任务并使用 R4 新建 / 取消”。保留旧任务快照，绝不能把旧结果改标为 R4。此问题不需要引入复杂调度系统即可解决。

## 二、需求覆盖判断

| 需求 | 本轮判断 | 说明 |
| --- | --- | --- |
| 画面与规则联动、节点就地编辑 | 基本满足前端演示 | 中小视口需要简化布局和滚动 |
| A/B 证据可见、AND/OR 组合 | 部分满足 | 关联字段变化缺少同步来源与核对机制 |
| 条件 / 分支分别设置时间 | 已有基础 | 应收敛到同一个完整时间编辑器 |
| 顺序、并行及嵌套编排组 | 已有编辑基础 | 不代表已完成真实视频时序执行验收 |
| 任意数量条件、NOT、分支内嵌套及新增业务条件 | 尚不完整 | 现有固定示例编辑不等于通用编排器 |
| 业务输出来源和类型受控选择 | 基本满足前端目标 | 仍需真实执行数据契约验收 |
| 草稿 / 已应用 / 运行版本分离 | 部分满足 | 活动旧任务与新版本启动存在歧义 |
| 校验问题定位、未保存保护 | 已有可用基础 | 校验需覆盖语义关联项，不只是结构与数值 |
| 完整保存 / 加载 / 版本历史 | 尚未完整验收 | 12 页等后续工作，先解决配置一致性 |
| 统一模型接入、插件 / 能力管理 | 本轮未形成完整用户流程 | 不应根据侧栏存在就宣称已实现 |
| 自然语言重新编排、真实推理及事件效果 | 本阶段未接入 | 不用模拟结果代替真实验收 |

## 三、建议优先级与验收标准

### P1：先修一致性，不增加新页面

1. **说明与规则分离**：修改说明不能让用户误认为规则已更新；重新编排有明确入口、差异审阅和未接入状态。
2. **条件关联字段核对**：修改目标、属性、部位、来源时，自动生成字段与自定义字段使用不同更新策略；存在冲突必须可见，不静默覆盖用户定制。
3. **运行版本明确选择**：R4 启动遇到 R3 活动任务时先选择；界面版本、任务快照和结果版本始终一致。

### P2：减少理解与操作成本

1. 统一“查看未应用修改 → 校验 → 应用”的差异审阅入口。
2. 简化运行入口，查看快照与开始运行分开。
3. 合并时间编辑入口；保留清晰的作用对象和模式相关字段。
4. 中小视口采用明确分区，减少多层滚动，画布能适应可用空间。
5. 补齐通用条件树和新增条件入口，然后再扩大能力类型，不为每种业务堆独立页面。
6. 高级提示词、切片 / 去重参数与技术 ID 分层展示；保留用户可控配置与解释。
7. 未实现入口标记状态，清理过期说明。

后续顺序：P1 一致性修复 → P2 核心交互收敛 → 12 完整保存与加载 → 其余页面及真实后端接入。

## 四、可访问性与操作风险

- 已观察到未保存保护对话框与表单控件可通过可访问性树识别，这是良好基础。
- 中小视口多层滚动会增加键盘和放大使用者的定位成本；需验证焦点始终可见且不会被固定页脚遮挡。
- 画布缩放等控件存在英文名称，应统一中文名称与工具提示；图标入口要能明确表达操作对象。
- 多边形顶点的完整键盘编辑、数值替代输入尚未验收；不能仅因鼠标能拖动就认定所有用户可操作。
- 本轮未完成全流程纯键盘、屏幕阅读器、200% 缩放和对比度逐项测量，不作 WCAG 合规结论。
